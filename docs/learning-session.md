# Навчальна сесія: як працює Home Dashboard

Ціль: навчитися простежувати дію користувача до стану, мережевого запиту й оновлення екрана, а також розуміти, де шукати помилки. Орієнтир — 60–75 хвилин; темп можна змінювати.

Відкрийте [інтерактивний огляд](archify/overview.html) та [каталог схем](archify/README.md). HTML працює локально; посилання на вихідний код ведуть на зафіксований commit GitHub. Для читання без браузерного Viewer є SVG у каталозі схем.

## 1. Система загалом — 10 хвилин

Почніть зі [загальної схеми](archify/overview.html). На ESP32 працюють і мережеві клієнти, і UI. Три workers незалежно отримують погоду, тривоги й відключення. Дані сходяться у спільному стані в RAM; UI читає його копію. NVS зберігає налаштування після вимкнення живлення.

Пройдіть шлях «Погода → Спільний стан → Екран LVGL». Зверніть увагу на напрямок стрілок: до зовнішнього API спрямовано запит, до snapshot — результат, до UI — копію даних. HTTP не виконується в touch callback.

Питання для самоперевірки: якщо Alerts.energy відповідає повільно, чи зупиниться погода? Ні: це різні задачі з власними HTTP-ресурсами. Усередині одного alerts worker карта й active.json виконуються послідовно, бо ділять кеші, покоління та бюджет.

Код для читання: [app_main](../main/dashboard.c), [workers та supervisor](../main/dashboard_data.c), [контракт snapshot](../main/dashboard_data.h).

## 2. Межа між мережею та UI — 10 хвилин

Відкрийте [схему взаємодії](archify/interaction.html). Worker отримує body, парсер перетворює його у bounded C-структуру, потім worker коротко бере data_lock і публікує стан. LVGL timer раз на секунду викликає dashboard_data_snapshot.

Чому не тримати lock протягом HTTP? Запит може тривати секунди, а spinlock захищає лише коротку операцію копіювання/публікації. Довге очікування під ним завадить іншим контекстам. Парсинг і NVS теж виконуються поза ним.

Чому існує окремий dashboard_data_alert_details? Локальні records не кладуть у звичайний snapshot, щоб не збільшувати робочі копії на стеку UI. Окрема копія перевіряє, що вона сумісна з очікуваними даними.

Самоперевірка: чи означає збережена температура, що дані свіжі? Ні: потрібно врахувати state, timestamp, offline та recovery. Значення, свіжість і працездатність задачі — три різні речі.

## 3. Розберіть гонку A → B → A — 10 хвилин

Відкрийте [схему локації](archify/location.html). Уявіть: запит для Дніпра почався на generation 7; потім обрано Львів, а потім знову Дніпро. Поточний generation уже 9. Відповідь першого запиту не застосовується, хоча місто збігається.

Це показує, чому одного порівняння city ID недостатньо. Покоління позначає конкретну версію вибору, а не лише його значення. Такий самий принцип захищає графік енергії та запити каталогу.

Простежте збереження: UI → Data API → NVS commit → публікація нового міста. Якщо commit не вдався, застосований стан не змінюється. Вибір міста не змінює чергу відключень: це незалежна конфігурація.

Самоперевірка: чи можна перемиканням міста обійти паузу після помилки API? Ні: generation переносить звичайний розклад, але service backoff зберігається.

## 4. Тривоги та графік — 15 хвилин

На [схемі тривог](archify/alerts.html) знайдіть два endpoint. Карта повідомляє статуси територій, active.json — записи й типи загроз. Зміна карти робить старі details несумісними й планує urgent-запит у межах спільного бюджету. 304 має сенс лише тоді, коли вже є валідний кеш.

Значки ракети чи БпЛА — категорії загроз території. Вони не задають координати цілей. Масив із 78 елементів — простір ISO-індексів, а не 78 областей. UID API, ISO-код і КАТОТТГ не взаємозамінні.

На [схемі відключень](archify/energy.html) розрізніть draft майстра й застосований selection. Поки користувач вибирає область і оператора, чинний вибір залишається. Лише вибір черги та успішний commit змінюють selection і energy_generation.

Графік — дві доби по 48 півгодинних слотів. CLEAR/POSSIBLE/OFF задають стан слота; WAITING/PLANNED/NO_SHUTDOWNS/EMERGENCY — стан доби. Відсутність опублікованого графіка не означає відсутність відключень.

Самоперевірка: чому каталог має окремий generation? Користувач може закрити або змінити крок майстра, не змінюючи застосований графік; пізня відповідь каталогу вже не потрібна цьому UI.

## 5. Wi-Fi, екран і recovery — 15 хвилин

[Wi-Fi](archify/wifi.html): телефон надсилає credentials локальній HTTP-формі у SoftAP. Provisioning manager підключає станцію; event loop обробляє результат і зберігає налаштування. Браузер не бере участі в щоденному відображенні дашборда.

[Екран](archify/display.html): чиста модель вирішує, чи потрібні нічна яскравість, сон і пробудження. LVGL застосовує результат через callback до LEDC. Перший дотик сплячого екрана поглинається, щоб разом із пробудженням не натиснути випадкову кнопку.

[Recovery](archify/recovery.html): heartbeat означає, що задача просувається, а не те, що інтернет працює. Offline чи відсутній ключ самі по собі не є зависанням. Supervisor запитує відновлення після 45 с без heartbeat; 15 с без завершення дають FAILED. pending при цьому лишається; worker може повернутися пізніше.

Самоперевірка: чому supervisor не закриває чужий HTTP client? Worker може ще використовувати його. Власник сам помічає скасування, завершує client і перепідготовляє свої буфери. Повний reboot є окремою дією.

## 6. Карта коду й практична вправа — 10–15 хвилин

Відкрийте [модель структур](archify/types.html) і [довідник модулів](architecture-reference.md). Тут немає класів C++; record означає typedef struct, а функції модулів описані окремо.

Спробуйте без зміни коду відповісти, де додати новий мережевий показник:

1. Визначити модель результату та правило свіжості.
2. Додати bounded parser, який відхиляє невідомий або пошкоджений формат.
3. Обрати власника HTTP і його бюджет/backoff. Новий endpoint не обов'язково означає нову задачу.
4. Публікувати перевірений результат під коротким lock, враховуючи generation, якщо дані залежать від вибору.
5. Оновити UI через snapshot, показавши waiting/stale/error, і перевірити пам'ять на пристрої.

Орієнтир відповіді: парсер не повинен малювати UI; touch callback не повинен виконувати HTTPS; додавання поля в структуру не вирішує планування, свіжість і помилки. Межі існуючих тестів та перевірок на платі описані в [архітектурі](architecture.md).
